### 项目描述
基于 C++17 和 Qt 框架开发的客户端/服务端架构即时通讯系统，实现了完整的聊天、文件传输、群聊等功能。项目采用自定义 TCP 协议，解决了网络编程中的粘包问题，使用 Model/View 架构实现现代化聊天界面，支持多线程文件传输和断点续传。

### 技术栈
C++17 | Qt 5.15 | CMake | MySQL | TCP/IP | 多线程编程 | 网络编程

### 主要职责与成果

#### 1. 网络通信模块（核心）
- 设计并实现自定义 TCP 应用层协议，使用固定长度协议头（PDUHeader）解决粘包/半包问题
- 实现心跳包机制（客户端 5 秒发送，服务端 15 秒超时检测），保证连接稳定性
- 开发断线重连功能，采用指数退避算法（初始 5 秒，最大 30 秒），自动恢复登录状态
- 使用 Qt 信号槽机制实现异步网络通信，避免阻塞主线程

#### 2. 聊天界面开发
- 基于 Qt Model/View 架构实现聊天界面，继承 QAbstractListModel 管理聊天数据
- 自定义 QStyledItemDelegate 绘制气泡聊天界面，支持文本、图片消息的左右对齐显示
- 实现历史消息查询和离线消息推送功能，消息持久化存储到 MySQL 数据库
- 支持私聊和群聊功能，群聊消息显示发送者用户名

#### 3. 文件传输系统
- 使用 QThread 实现多线程文件传输，采用 64KB 分片传输，避免 UI 阻塞
- 开发断点续传功能，使用位图记录已接收分片，传输状态持久化到 JSON 文件
- 实现文件传输进度实时显示，支持取消传输和传输失败重试
- 通过信号槽跨线程通信更新主线程进度条，保证界面流畅

#### 4. 服务端开发
- 使用 QTcpServer 实现多客户端并发连接，维护在线用户列表（QMap<int, QTcpSocket*>）
- 实现消息路由转发功能，根据目标 ID 查找对应 Socket 进行消息转发
- 设计数据库表结构（用户表、好友表、消息表、群聊表等），实现数据持久化
- 实现离线消息存储和推送机制，用户上线后自动推送离线消息

#### 5. 系统设计与优化
- 采用单例模式设计 NetworkManager、FileTransferManager、ConfigManager 等核心模块
- 实现 JSON 配置文件管理，支持灵活配置服务器地址、端口、心跳参数等
- 开发多级别日志系统（DEBUG/INFO/WARN/ERROR），支持文件输出和线程安全
- 使用 SHA-256 + Salt 实现密码安全存储，消息传输采用 XOR 加密

## 🎯 面试问题准备

### 问题 1：TCP 粘包问题你是怎么解决的？

**回答要点**：
1. **问题分析**：TCP 是流式协议，没有消息边界，多个小包可能合并成一个大包（粘包），或者一个大包被拆分成多个小包（半包）
2. **解决方案**：
   - 设计固定长度协议头（PDUHeader，16 字节），包含 total_len、msg_type、dest_id、src_id
   - 接收端先读取协议头，解析出完整包长度
   - 使用 QByteArray 作为接收缓冲区，等待数据足够后再读取完整包体
   - 如果缓冲区数据不足，等待下次 readyRead 信号继续接收
3. **代码示例**：
```cpp
void NetworkManager::onReadyRead() {
    while (m_socket->bytesAvailable() >= sizeof(PDUHeader)) {
        // 先读取协议头
        PDUHeader header;
        m_socket->peek((char*)&header, sizeof(PDUHeader));
        
        // 检查是否接收完整包
        if (m_socket->bytesAvailable() < header.total_len) {
            return; // 数据不完整，等待下次
        }
        
        // 读取完整包
        QByteArray packet = m_socket->read(header.total_len);
        processPacket(packet);
    }
}
```

### 问题 2：文件传输为什么用多线程？如何实现的？

**回答要点**：
1. **为什么用多线程**：
   - 大文件读取和发送是 I/O 密集型操作，会阻塞主线程
   - 主线程负责 UI 渲染，阻塞会导致界面卡顿、无响应
   - 多线程可以在后台处理文件传输，主线程继续响应用户操作
2. **如何实现**：
   - 继承 QThread 创建 FileTransferThread 类
   - 在 run() 方法中循环读取文件并发送分片（64KB）
   - 使用信号槽跨线程通信：emit progressUpdated(percent) 更新进度条
   - 主线程通过 connect 连接信号，更新 UI 组件
3. **线程安全**：
   - 使用 QMutex 保护共享数据（如传输状态）
   - 避免在子线程直接操作 UI 组件

### 问题 3：心跳包的作用是什么？如何实现的？

**回答要点**：
1. **作用**：
   - 检测连接是否存活（TCP 连接可能因为网络问题"假死"）
   - 及时发现网络异常，触发断线重连
   - 服务端可以清理僵尸连接，释放资源
2. **实现机制**：
   - 客户端：使用 QTimer 定时发送心跳包（默认 5 秒）
   - 服务端：每次收到心跳包重置超时定时器（默认 15 秒）
   - 超时未收到心跳包，服务端主动断开连接
3. **代码示例**：
```cpp
// 客户端
m_heartbeatTimer = new QTimer(this);
connect(m_heartbeatTimer, &QTimer::timeout, [=](){
    NetworkManager::instance().sendMsg(MSG_HEARTBEAT_REQ, QByteArray());
});
m_heartbeatTimer->start(5000); // 5 秒发送一次

// 服务端
void ClientSocket::onHeartbeatReceived() {
    m_timeoutTimer->start(15000); // 重置超时定时器
}
```

### 问题 4：断点续传如何实现的？

**回答要点**：
1. **核心思路**：
   - 使用位图（bitmap）记录已接收的分片（每个 bit 表示一个分片）
   - 传输状态持久化到 JSON 文件（文件 ID、总分片数、已接收分片等）
   - 断线重连后，发送恢复请求（MSG_FILE_RESUME_REQ）
   - 服务端返回已接收分片的位图（MSG_FILE_RESUME_RESP）
   - 客户端只发送未接收的分片
2. **协议设计**：
```cpp
struct FileResumeResp {
    char fileId[64];         // 文件 ID
    quint8 canResume;        // 是否可以恢复
    quint32 totalChunks;     // 总分片数
    quint32 receivedChunks;  // 已接收分片数
    // 后面跟着位图数据
};
```
3. **位图操作**：
```cpp
// 设置第 n 个分片已接收
bitmap[n / 8] |= (1 << (n % 8));

// 检查第 n 个分片是否已接收
bool received = (bitmap[n / 8] & (1 << (n % 8))) != 0;
```

### 问题 5：你的协议设计有什么考虑？

**回答要点**：
1. **协议头设计**：
   - 固定长度（16 字节），便于解析
   - total_len：包含头部和包体的总长度，用于解决粘包问题
   - msg_type：消息类型枚举，便于路由和处理
   - src_id 和 dest_id：源和目标用户 ID，便于消息转发
2. **字节对齐**：
   - 使用 `#pragma pack(push,1)` 确保结构体紧凑排列
   - 避免不同平台字节对齐差异导致的解析错误
3. **扩展性**：
   - 消息类型使用枚举，便于添加新消息类型
   - 包体使用 QByteArray，支持任意长度和格式的数据
   - 子类型机制（SUB_TEXT、SUB_IMAGE）支持同一消息类型的不同内容

### 问题 6：如何保证消息不丢失？

**回答要点**：
1. **离线消息机制**：
   - 服务端检测目标用户是否在线
   - 不在线则存储到 offline_messages 表
   - 用户上线后，服务端自动推送离线消息
2. **历史消息存储**：
   - 所有消息持久化到 chat_messages 表
   - 客户端可以查询历史记录（默认最近 200 条）
3. **传输确认机制**：
   - 文件传输使用分片确认（MSG_FILE_TRANSFER_ACK）
   - 确保每个分片都被接收

### 问题 7：项目中遇到的最大挑战是什么？如何解决的？

**回答示例**：
最大的挑战是实现断点续传功能。一开始我只是简单地记录已发送的分片数量，但发现网络不稳定时，某些分片可能丢失，导致文件损坏。

**解决方案**：
1. 改用位图记录每个分片的接收状态，而不是简单的计数
2. 传输状态持久化到 JSON 文件，避免程序崩溃导致状态丢失
3. 实现文件校验机制（MD5），确保传输完整性
4. 添加重试机制，失败的分片自动重传

这个过程让我深刻理解了网络传输的不可靠性，以及如何设计健壮的传输协议。
